# Project workflows

Use the actual repository and runtime to choose a workflow. Pocket Harness routes explicit task domains and project manifests to this guide and the installed specialist skills; it does not imply that any external service, model, browser or deployment connection exists. Inspect current `pocket kit` help and installed command help before using a capability.

## One execution contract

1. **Discover once.** Recover the requested outcome and earlier completed work. Inspect dirty state, project instructions, the changed owner, manifests, lockfiles, runtime versions, existing tests and delivery configuration. Reproduce a reported failure before changing its cause. For performance work preserve a representative baseline with wall time, correctness, tool calls and available token/coordination accounting. Parallelize independent bounded reads, then consume every result.
2. **Implement at the owner.** Match neighboring conventions and existing dependencies. Use one writer per overlapping file. A simple task gets a direct implementation; ambiguous, risky or failing work gets deeper reasoning, focused specialists or one independent review. Add parallel agents only when their work is independent and the saved time exceeds the handoff/context cost. Available local models and JEV can advise on a precise unresolved question; deterministic facts come from commands and tests.
3. **Validate the changed behavior.** Run the smallest relevant check, its failure case and the deliverable's real startup/build path. Broaden to required project/CI checks for shared contracts or release changes. Reassess on failures: collect the actual error, narrow the cause, then escalate; repeating the same review or command without new evidence adds no assurance. UI work gets real interaction and visual checks, established identity and one focused anti-slop pass.
4. **Deliver the verified artifact.** Complete authorized Git/release/installation/deployment steps, then check the delivered artifact itself. A source test does not prove the installed binary or production site contains that revision. Report version/revision, executed checks and remaining unknowns. Publishing artifacts or paid/cloud operations must remain inside the user's existing authorization.

Track completion in the existing task/todo/session mechanism, with the artifact or revision and check that earned completion. Read that state before a subtask or resumed turn. Skip a completed phase when its inputs and checked artifact are unchanged; invalidate only phases whose dependencies changed. A small edit needs no new ledger or orchestration framework. Keep handoffs to the objective, owned files, relevant facts, completed checks and unresolved question.

Read only the relevant recipe in [stack workflows](references/stacks.md). The recipes cover PHP 8+, Node.js, vanilla JavaScript, React with CDN or Node tooling, Go, Rust, Java, Python/Flask, Bash, C/C++, Linux applications, local webapps, algorithm/ML design and local/Colab fine-tuning. Use [shared hosting deployment](../shared-hosting-deployment/SKILL.md) for Namecheap, GoDaddy or other Git/SSH shared hosts.

For video, animation, music and sound, load the relevant `video-studio`, `browser-animation-engineering`, `music-composition` or `audio-processing` guide. Use a low-cost preview before a final render, reuse measured timing/cues and source assets, and verify the exported media. Audio-only editing does not require a video publishing layer.

Stop adding coordination when the result is correct and the required delivery checks pass. Performance claims must compare the same workload and correctness standard; missing token accounting stays unavailable, and regressions require investigation before a speed claim.
