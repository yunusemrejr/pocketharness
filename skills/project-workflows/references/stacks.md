# Stack recipes

Select the row that matches the existing project. Commands below are validation examples, not permission to replace the build system or install every listed tool. Read installed version/help and the project scripts; run only applicable checks. Discovery and delivery follow the common contract in [Project workflows](../SKILL.md).

| Stack | Discovery and implementation | Validation and delivery |
| --- | --- | --- |
| PHP 8+ | Inspect `composer.json`/lock, CLI and web-SAPI PHP versions, extensions, framework, document root and session/storage behavior. Match the supported PHP 8.x range; isolate request validation, authorization, parameterized SQL and escaped output. Load `php-application-engineering`. | Lint changed PHP files with `php -l`; run existing Composer/test scripts and an actual request through the selected SAPI. Build dependencies from the lockfile; keep source/secrets outside the public root. Verify deployed PHP version, error handling and writable paths. |
| Node.js | Inspect engines, package type, lockfile, scripts and production entrypoint. Assign cleanup/cancellation to async work, streams and subprocesses. Use the existing package manager and `node-runtime-engineering`. | Run existing tests and build; exercise production startup, shutdown and one error request. Verify packaged execution, including lockfile install and missing environment behavior. Do not ship a development server as production. |
| Vanilla frontend JavaScript | Inspect the real HTML/CSS/DOM, module loading and browser support. Preserve native controls and current layout; use `browser-javascript-engineering` for bounded effects, stale requests and teardown. | Check console/network errors, keyboard/focus, responsive overflow and the changed user journey in a real browser. Serve from HTTP when modules/fetch require it. Verify the delivered files, caching and paths, including a nested URL. |
| React through CDN | Confirm an existing CDN/import-map or ESM arrangement; pin compatible React/ReactDOM versions. Production uses precompiled JavaScript or compatible `createElement` calls; browser Babel is for an explicitly chosen prototype. Keep secrets and server logic outside the client. Load `modern-frontend-frameworks`. | Exercise mount/unmount, state/error paths and actual hosting/CSP/network behavior. Check that dependency versions resolve without a development build step. Deliver static assets/import map and document the dependency boundary. |
| React with Node tooling | Inspect framework/rendering model, versions, package scripts, lockfile and backend contract. Keep server/client code and ownership distinct; extend existing components and state rather than introducing another framework. | Run project tests and production build/start. Check hydration, routing, refresh at nested URLs and empty/error/loading states against the actual backend. Deploy the built static bundle or supported server runtime. |
| Go | Inspect `go.mod`, toolchain, package boundaries, build tags and service/CLI entrypoint. Use `go-service-engineering` for context cancellation, ownership and bounded concurrency. | Run `go test ./...` and `go vet ./...` where required; build and exercise the binary. Add `-race` for changed shared state. Deliver the selected GOOS/GOARCH artifact and verify startup/shutdown on its actual target. |
| Rust | Inspect `Cargo.toml`/lock, toolchain/features, error conventions and unsafe boundaries. Use `rust-systems-engineering`; preserve ownership and avoid unchecked conversions at boundaries. | Run project `cargo test`, `cargo fmt --check` and configured Clippy checks; build release with required features and execute it. Check target/linker and dynamic-library requirements before packaging. |
| Java | Inspect Maven/Gradle wrapper, JDK release/toolchain and entrypoint. Use `java-platform-engineering`; bound executor work and own resource cleanup. | Use the repository wrapper's tests and package target. Execute the actual JAR/application with the supported JRE, check shutdown and resource paths, then deliver JAR/runtime/native package as requested. |
| Python/Flask | Inspect `pyproject.toml`, requirements/lock, interpreter, virtual environment and import layout. Use `python-software-engineering`; preserve Flask app factory/config and request/session contract. | Run existing tests and import/CLI smoke checks in the chosen environment. For Flask use the test client for success/error/auth paths, then the intended WSGI startup. Deliver locked dependencies; do not expose the Flask debugger in production. |
| Bash | Inspect shebang, supported shell, input/exit contract and subprocess dependencies. Load `bash-workflows`; quote expansions and make failure/cleanup ownership explicit. | Run `bash -n`, available ShellCheck and a bounded fixture containing spaces/empty values plus one command failure. Execute from the intended working directory and deliver an executable with its required commands documented. |
| C/C++ | Inspect Make/CMake/Meson configuration, compiler standard, platform ABI, ownership and existing tests. Use `c-systems-engineering`, `cpp-performance-engineering` or `c-cpp-multiplatform` as appropriate; keep native dependencies minimal. | Run warning-clean build and behavioral tests; use sanitizers for changed memory/integer lifetimes and concurrency checks for shared state. Benchmark optimized release builds against the same correctness oracle. Install/package and verify binary/version plus runtime libraries. |
| Linux-native application | Discover the existing toolkit (GTK/Qt/FLTK/native terminal), display backend, event loop and packaging. Use `linux-desktop-ui-ux` and the language guide; preserve platform input, accessibility and project identity. | Check keyboard/focus, scaling, resize, long text, empty/error states, launch and close. Test the actual executable and installed desktop entry/icons/assets; UI screenshots alone cannot verify event-loop responsiveness. |
| Local webapp | Inspect available ports, entrypoint, storage, browser and lifecycle. Load `local-webapp-workflows`; bind to loopback, preserve existing process state and keep launch/cleanup ownership clear. | Wait for real HTTP readiness, run the main user path and persistence/error cases, inspect console output, then verify restart and documented launch/stop commands. External exposure requires the authorized delivery scope. |
| Algorithm design | State workload bounds, exactness and invariants; implement a simple oracle before optimizing. Load `algorithm-design`, with `optimization-modeling`/`numerical-computing` when relevant. | Compare small generated/adversarial inputs against an independent oracle. Measure time/memory across representative sizes and keep correctness unchanged; deliver the assumptions, complexity and measured boundary. |
| AI/ML design | Inspect target metric, data provenance, split/lineage and deployment budget. Use `ml-engineering`, appropriate classical/hybrid/NLP skill and `model-evaluation`; start with a simple baseline. | Prevent split leakage; evaluate frozen slices, calibration/errors and resource cost. Deliver reproducible data/model/config revisions and actual inference behavior, including limitations. A training score does not establish held-out quality. |
| Local/Colab fine-tuning | Discover available local hardware or an actually connected Colab runtime. Load `llm-fine-tuning`, `llm-dataset-preparation` and `google-colab-training` for that target; choose method from measured memory, immutable model revision and validated masks. | Run a small forward/backward/save/reload/resume smoke test before the substantial run. Compare base/tuned/exported models on frozen prompts. Deliver notebook/module, exact environment/data revisions, durable checkpoints and runtime status. A prepared notebook is not evidence that Colab training ran. |

Git/GitHub delivery applies when present: inspect remote/branch, respect unrelated changes, run required CI checks, commit the owned change, publish the authorized version/tag/release or PR, then verify its artifact. For a shared host use the dedicated hosting guide and its actual Git/SSH configuration; never assume provider branding determines server capabilities.
