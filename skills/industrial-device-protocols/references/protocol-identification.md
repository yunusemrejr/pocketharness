# Identify the protocol before interpreting the value

Start with passive evidence: vendor model, firmware revision, wiring diagram, interface settings, network capture and configuration export. Record what is observed versus inferred. Ethernet, RS-485 and CAN describe different layers or transports; a physical connector alone does not identify the payload schema. Do not try multiple write commands until one appears to work. Use an offline decoder or an explicitly authorized read-only query against the known target when more evidence is needed.

Modbus provides function-coded requests and responses over transports including serial and TCP. Distinguish coils, discrete inputs, input registers and holding registers. Register notation in a manual may use one-based presentation while a protocol request carries an offset; document the translation once. Multi-register application types and word order require the vendor mapping. Modbus TCP framing and serial CRC framing differ, so do not append a serial CRC to a TCP application data unit by habit. Use the current Modbus specification and device manual together. [Modbus specifications](https://www.modbus.org/modbus-specifications).

OPC UA exposes typed nodes and services, not simply an array of registers. Preserve namespace identity, NodeId, browse context and data type. A DataValue can carry a value, status and source/server timestamps; the value alone cannot establish freshness or quality. Treat server trust and session configuration as part of the connection contract. Do not accept arbitrary certificates or downgrade security merely to complete a test. [OPC UA DataValue specification](https://reference.opcfoundation.org/specs/OPC-10000-4/7.11).

MQTT is brokered publish/subscribe transport. Topics and payload meaning come from the application or a higher-level convention; MQTT does not prescribe that a payload is JSON or a measurement. Account for retained messages, session behavior and QoS when interpreting delivery. A retained value can be old, and transport acknowledgment does not prove an actuator executed a command. Distinguish message expiry from an application measurement timestamp. [OASIS MQTT 5.0](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html).

CAN frames use identifiers and bounded payloads; higher-level meaning may come from a DBC, CANopen object dictionary, J1939 conventions or proprietary documentation. Distinguish classic CAN and CAN FD and verify bit-rate and identifier-width configuration. Do not infer that a bus acknowledgment proves application acceptance. Payload interpretation needs signedness, start bit, bit length, byte order, scaling, offset and multiplexing definitions from the correct device revision. [CiA CAN FD overview](https://www.can-cia.org/can-knowledge/can-fd-the-basic-idea).

EtherCAT uses cyclic process data and device-state machinery with topology and timing requirements. Treat an ESI description, PDO mapping and configured state as part of the decoder contract; a generic Ethernet parser is insufficient. Distributed clocks provide a synchronization mechanism, but actual timing must be verified in the specific setup. A state transition or process-data write can affect equipment and belongs to an explicitly authorized control workflow. [EtherCAT Technology Group overview](https://www.ethercat.org/en/technology.html).
