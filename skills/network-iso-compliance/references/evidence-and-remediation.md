# Evidence sampling, findings and remediation

## Evaluate operation over time

A screenshot can show a configuration at one moment; it rarely proves a control operated throughout an assessment period. Select evidence appropriate to the control: change records for rule governance, identity records for access management, restore results for recovery, or incident exercises for response capability. Define the population, sample selection and time interval. A convenient sample of successful events is not representative evidence. Include failed, exceptional and emergency cases when they are relevant to the control objective.

Maintain a source ledger with file identifier, acquisition date, owner, period covered, scope, integrity hash where useful, and sensitivity. Preserve links to original records rather than copying large sensitive exports into agent context. Record redactions and their effect on verification. Names, network addresses, credentials and customer records may need restricted handling; an assessment request does not authorize publication. Technical tools produce observations that should be corroborated with organizational records.

## Write findings that can be resolved

A useful finding states the assessed objective, observed condition, supporting evidence, affected scope and practical risk. Separate a confirmed gap from a documentation question or testing limitation. Avoid assigning severity solely from a scanner label. Consider exposure, asset purpose, existing controls, exploitation preconditions and business impact using the organization's risk method. Do not invent numerical likelihood or regulatory penalties to make a finding look precise.

For each action, identify an owner, intended outcome, implementation dependency, target date and evidence of completion. Prefer acceptance criteria tied to behavior: unauthorized cross-segment access is denied for the agreed test cases and approved paths continue to operate. Installing a named product is not an outcome. If a compensating control is proposed, state which risk it reduces and which residual exposure remains for the accountable owner to consider.

## Retest and close with evidence

Recheck the same scope and acceptance criteria after remediation, then test relevant legitimate behavior to detect regressions. Preserve the before/after artifacts and change reference. A closed ticket without technical or process evidence is not a demonstrated fix. Conversely, a technical fix may leave training, ownership or review cadence incomplete. Mark partial closure clearly. If an action cannot be completed, document the blocker and risk-owner decision instead of quietly dropping the item.

The [ISO/IEC 27001 official description](https://www.iso.org/standard/27001) explains the management-system focus; [ISO/IEC 27002](https://www.iso.org/standard/75652.html) provides control guidance. Use legitimately available engagement material for exact requirements and audit terminology. An agent can prepare evidence, assess gaps and support readiness, but an internal technical report is not an accredited certificate.

Summarize coverage in counts that retain denominators: controls assessed, controls not assessed, evidence gaps, unresolved findings and accepted exceptions. A percentage without applicability and sampling context is misleading. End with a reviewable evidence matrix, residual uncertainties and the next concrete actions for responsible people.
